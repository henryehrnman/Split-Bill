Backend plan (draft for discussion; nothing here is built yet)
  Goal: replace the fake backend in mobile/src/lib/api.ts with a real server, without changing the product rules in schema.txt. The app already calls a small async API, so each method below becomes an HTTP endpoint. Business rules stay in mobile/src/lib/domain.ts and split.ts and move to the server as-is (TypeScript), so the server and the app's previews never disagree.
  Stage: hackathon MVP. Everything involving money runs in sandbox / test mode only. No live cards or real bank debits until we have a partner and the compliance questions in section 7 are answered.

  0) at a glance
    i) Server: TypeScript API (Hono) that imports domain.ts and split.ts unchanged, hosted on Vercel / Railway / Fly.io.
    ii) Database, sign-in, live updates, receipt storage: Supabase (Postgres + Auth + Realtime + Storage). Live updates matter for the claim board so locks and suggested edits show up on everyone's phone right away. [Alternative: Neon + Clerk + Ably.]
    iii) Cards: Stripe Issuing in test mode. Each card tap is sent to us in real time and we approve or decline within about 2 seconds; that is where the nonnegative-member-balance requirement, available pooled funds, suspension and frozen-group rules are enforced. [Alternative: Lithic, quicker sandbox access.]
    iv) Pulling money from members' banks (deposits, period refills): Stripe Financial Connections + ACH. [Alternative: Plaid.] When a confirmed split takes someone below $0, their personal card on file is charged back to $0 (schema 3.iii): a Stripe PaymentIntent on a saved card, which succeeds or fails in seconds instead of days.
    v) Ledger: our own append-only table of balance changes in Postgres; balances are calculated from it, never edited directly.
    vi) Scheduled jobs (period rollover, 7-day deadline, retrying failed charges): Inngest or Trigger.dev. [Simpler: Vercel Cron.]
    vii) Receipt scanning: a vision model (OpenAI, Claude or Gemini) returning structured JSON, checked against the charge total. [Alternative: AWS Textract.]
    viii) Notifications and invites: Expo Push, Resend (email), Twilio (SMS).
    ix) Two real-world problems the design must handle:
      a) Final amounts differ from the tap. Restaurants and gas stations often capture a different amount than they authorized (tips, holds), so the pending split updates when the final amount arrives, and acceptances/locks reset if it changed (3.ii).
      b) Bank debits are slow and can bounce. ACH takes 1-4 business days and can be returned after looking successful; a return feeds into the card-charge-or-suspend rule (3.iii).
    x) Biggest open decisions: Supabase vs separate services; Stripe vs Lithic; and pooled group money likely counts as money transmission, which is fine to ignore for the demo but needs a partner bank and legal review before a real launch (section 7).

  1) recommended stack (hackathon-friendly; alternatives in brackets)
    i) API server: TypeScript with Hono or Fastify, so domain.ts and split.ts are imported directly. Host on Vercel Functions, Railway or Fly.io. [Alternative: Supabase Edge Functions.]
    ii) Database: Postgres, hosted on Supabase or Neon. Money is stored as integer cents (as today). [Alternative: none recommended; we need transactions and row locks for balances.]
    iii) Auth: Supabase Auth or Clerk (both have Expo SDKs). Sign in with phone OTP or email. The signed-in user replaces the demo user switcher. [Phone OTP alternative: Twilio Verify.]
    iv) Realtime updates: Supabase Realtime (Postgres changes) so the claim board, locks, item edits and proposals update live on everyone's phone. [Alternatives: Ably, Pusher.]
    v) Card issuing: Stripe Issuing in test mode. One virtual card per member per group, with real-time authorization webhooks (see 3.i) so our rules approve or decline each tap. Apple/Google Wallet push provisioning needs extra approval from Stripe. [Alternatives: Lithic (good sandbox, developer-friendly), Marqeta, Highnote; Unit or Synctera if we want a bank-as-a-service partner that bundles accounts + cards.]
    vi) Bank linking and pulling funds (deposits, period refills): Stripe Financial Connections + ACH Direct Debit, so cards and funding are in one Stripe account. [Alternative: Plaid Auth + Balance for linking, then ACH through Stripe, Dwolla or Modern Treasury.] Debt recovery charges the member's saved personal card (Stripe SetupIntent at sign-up, PaymentIntent when needed).
    vii) Ledger: our own double-entry ledger tables in Postgres (section 4). Every balance change is a ledger entry; member balances are derived, never edited directly. [Alternatives if this grows: Modern Treasury Ledgers, Formance, TigerBeetle.]
    viii) Scheduled and background jobs: period rollover, 7-day split deadline, retrying failed bank and card charges, sending stale draft splits. Use Inngest or Trigger.dev (durable steps + retries). [Simpler: Vercel Cron or pg_cron calling an endpoint every few minutes.]
    ix) Receipt OCR (schema.txt 6.i.a): a vision LLM with structured JSON output (OpenAI, Anthropic Claude or Google Gemini), validated against the charge total. [Receipt-specific alternatives: AWS Textract AnalyzeExpense, Google Document AI, Veryfi, Mindee, Taggun.]
    x) Receipt image storage: Supabase Storage, S3 or Vercel Blob, private bucket, signed URLs.
    xi) Push notifications: Expo Push Notifications (works for both iOS and Android from the Expo app).
    xii) Invite emails / SMS: Resend for email, Twilio for SMS.
    xiii) Identity checks (required by card issuers for cardholders): Stripe Identity or Persona. Test mode only for now.
    xiv) Errors and logs: Sentry for the app and server.

    Fastest path for the hackathon: Supabase (Postgres + Auth + Realtime + Storage) + a Hono API importing domain.ts + Stripe (Issuing + Financial Connections + ACH, all test mode) + Inngest + Expo Push + one vision LLM.

  2) API endpoints (each maps to a method in mobile/src/lib/api.ts)
    All requests are authenticated; the actor is the signed-in user, never a field in the body. Every write takes an Idempotency-Key header so a retried tap can't double-charge or double-accept. Responses return the updated group state (same shape the app uses now) so the UI stays simple.
    i) Users and invites
      GET  /me                                   current user, groups, pending invites
      GET  /users/search?q=                      exact-ish match on username, email or phone (schema 1.i); returns minimal profile only
      POST /groups                               {name, inviteIds, budget, periodDays, initialContributionLimit}; record the creator’s reviewed maximum and create invitations without collecting money
      POST /groups/:id/invites/:inviteId/accept  {expectedContribution, initialContributionLimit}; record the reviewed maximum, join and issue card; final invite resolution starts the period and collects every joined member's final equal share once
      POST /groups/:id/invites/:inviteId/decline
    ii) Group and money
      GET  /groups/:id                           group, members, balances, standing, open charges, open budget proposal
      POST /groups/:id/deposits                  {amount}; additional member-authorized payment, available only after all invites resolve and at least two members join
      POST /groups/:id/withdrawals               {amount}; rejected while a split is pending (schema 3.i)
      PATCH /groups/:id/members/me               {autoDeposit}
      PATCH /groups/:id/default-split            {method, percents?}
      POST /groups/:id/budget-proposals          {amount}
      POST /budget-proposals/:id/respond         {accept}
    iii) Cards
      GET  /groups/:id/card                      my card (last4, frozen, wallet status); full card details only via Stripe's secure UI component
      POST /cards/:id/freeze  /cards/:id/unfreeze
      POST /cards/:id/wallet-provisioning        returns push-provisioning data for Apple/Google Wallet (needs issuer approval)
    iv) Charges and splits
      GET  /groups/:id/charges                   activity history
      POST /charges/:id/receipt                  upload image -> OCR -> line items (schema 5.i)
      PUT  /charges/:id/receipt                  fix items/tax/tip; releases all locks
      POST /charges/:id/items/:itemId/claim      toggle my claim
      POST /charges/:id/lock  /charges/:id/unlock
      POST /charges/:id/item-edits               {itemId, targetId}
      POST /charges/:id/item-edits/:editId/respond {accept}
      POST /charges/:id/proposals                {method, ...}   percent / amount / equal; while the charge is a draft only the cardholder can call this, and it sends the first proposal
      POST /charges/:id/send-default             cardholder sends the group's default split (also sent by the app when they leave, and by a job after 10 minutes); no-op once anything was sent
      POST /charges/:id/accept
      GET  /me/notifications                     recent proposal / receipt notifications (also delivered by push)
      POST /charges/:id/chargeback
    v) Internal (not callable by the app)
      POST /webhooks/stripe                      issuing authorizations, captures/transactions, ACH payment results, disputes
      POST /jobs/roll-periods  /jobs/enforce-deadlines  /jobs/send-stale-drafts   called by the scheduler

  3) how schema rules map to the backend
    i) Approving a card tap (schema 2.iv, 2.v): Stripe sends issuing_authorization.request in real time and we must answer within about 2 seconds. The handler runs purchaseBlocker() and spendLimit() from domain.ts: decline if the group is not active or is frozen, the member has a negative balance or is suspended, their card is unavailable, or the amount exceeds the group fund minus all unsettled charges. Zero-balance members may pay; period funding and proposed personal shares do not restrict purchases. Several purchases can remain open at once. Approve otherwise and create the pending charge as the cardholder's draft (sent_at null); nobody else is notified until the cardholder sends the first proposal or the default split goes out.
    ii) Authorization vs final amount: restaurants and gas stations often capture a different amount than they authorized (tips, pre-auth holds). The pending charge starts at the authorized amount; when the final transaction arrives we update the charge amount and, if it changed, reset acceptances and locks. Refunds create a credit split back by the agreed shares.
    iii) Deposits and refills (schema 1.i, 1.iii): ACH debits take 1-4 business days and can be returned (e.g. insufficient funds) after looking successful. For the MVP, credit the member's balance when the debit is initiated, and treat a later return like a failed charge (balance drops back; if negative, start debt recovery / suspension). Record both events in the ledger.
    iv) Settling a split (schema 3.i-3.iii): one database transaction: lock the group row, apply each share as a ledger entry, and if anyone goes negative charge their saved personal card the amount needed to bring them to $0. If that charge fails, mark the member suspended (they stay in the group; the group carries the debt).
    v) Period rollover (schema 1.iii): a scheduled job finds active groups whose period ended, starts refill debits for auto-refill members up to their share (leftover balance counts), and advances the period. The first period begins when the group becomes active; its initial equal contributions are collected once at activation, under the variable final-share terms shown before creation/joining. Failed initial charges are recorded per member without undoing successful payments. Members whose balance reaches their share are marked funded for that period (memberships.funded_period); this is funding history only and does not determine purchase eligibility. Idempotent per group + period so a rerun can't charge twice.
    vi) 7-day deadline and chargebacks (schema 4.i, 4.ii): the deadline job freezes groups with a pending split older than 7 days. Stripe Issuing dispute / chargeback webhooks freeze the group. Freezing also blocks authorizations immediately (3.i).
    vii) Claim board (schema 5.i): claims, locks and edits are rows; every change broadcasts over Realtime. When the last lock/edit resolves, the server confirms the split and settles in the same transaction, so two people locking at the same moment can't settle it twice.
    viii) First proposal and notifications (schema 2.i): a new charge is a draft until the cardholder sends a proposal, sends the default, or scans the receipt. The app calls send-default when the cardholder leaves the split screen or backgrounds the app; /jobs/send-stale-drafts sends it after 10 minutes as a fallback. Each sent proposal notifies only the members with a share (receipt scans notify everyone), via a notifications row + Expo push.

  4) data model (Postgres tables)
    users(id, name, handle unique, email unique, phone unique, created_at)
    groups(id, name, created_by, budget_cents, period_days, period_start, activated_at, default_split jsonb, frozen_reason, frozen_at)
    memberships(group_id, user_id, status invited|joined, initial_contribution_limit, auto_refill, suspended, funded_period, joined_at)  -- balance is derived from ledger
    cards(id, group_id, user_id, issuer_card_id, last4, frozen, wallet_status)
    bank_accounts(id, user_id, provider, provider_account_id, last4, status)
    charges(id, group_id, cardholder_id, issuer_authorization_id, merchant, amount_cents, status pending|settled|disputed, created_at, sent_at, settled_at)
    receipts(charge_id, image_path, tax_cents, tip_cents, itemized, scanned_at)
    receipt_items(id, charge_id, name, amount_cents)
    item_claims(item_id, user_id)
    item_locks(charge_id, user_id)
    item_edits(id, charge_id, item_id, target_id, action add|remove, author_id, created_at)
    proposals(id, charge_id, author_id, input jsonb, shares jsonb, created_at)
    proposal_acceptances(proposal_id, user_id)
    budget_proposals(id, group_id, author_id, amount_cents, created_at) + budget_acceptances
    ledger_entries(id, group_id, user_id, kind, amount_cents, charge_id, external_ref, created_at)  -- append-only
    notifications(id, user_id, group_id, charge_id, text, created_at, read_at)
    payment_methods(id, user_id, provider_payment_method_id, brand, last4)  -- personal card used for debt recovery
    payment_attempts(id, user_id, group_id, purpose deposit|refill|debt_recovery, amount_cents, provider_ref, status pending|succeeded|failed|returned)
    idempotency_keys(key, user_id, response, created_at)
    audit_events(id, actor_id, action, payload jsonb, created_at)

  5) security basics
    i) Server is the only source of truth for balances, standing and splits; the app only displays and sends requests.
    ii) Row-level checks on every endpoint: you can only read and act in groups you belong to; only the target of an item edit can answer it.
    iii) Never store card numbers or bank account numbers; keep only issuer/provider IDs and last4. Card details are shown via the issuer's secure component.
    iv) Verify webhook signatures and dedupe webhook events by ID (they can arrive twice or out of order).
    v) LLM calls (OCR, plain-English claiming) run server-side; outputs are drafts validated by domain.ts (schema 6).

  6) build order
    i) Phase 1 (no money): Postgres schema, auth, the endpoints in section 2 running domain.ts, Realtime for the claim board, and the app switched from the fake API to HTTP. Deposits are still simulated. This alone makes multi-phone demos real.
    ii) Phase 2: scheduler (period rollover, 7-day deadline), Expo push notifications, invite emails/SMS, receipt upload + vision OCR.
    iii) Phase 3 (test mode money): Stripe Issuing test cards + real-time authorization webhook, Financial Connections + ACH test debits for deposits and refills, saved-card charges for debt recovery, ledger reconciliation against Stripe.
    iv) Phase 4 (only with a partner): wallet push provisioning, KYC, live mode.

  7) open questions for the team
    i) Supabase vs separate services (Neon + Clerk + Ably)? Supabase is fastest to start.
    ii) Stripe vs Lithic for issuing in the demo? Stripe keeps cards and ACH in one place; Lithic's sandbox is quicker to get into.
    iii) Pooled group funds held for consumers likely count as money transmission / stored value. A live launch needs a sponsor bank or a BaaS partner (e.g. through the issuer) and legal review. Fine to ignore for the hackathon demo, not for launch.
    iv) Who pays when a suspended member never repays (schema 3.iii says the group carries it)? Do we ever write it off?
    v) Do we credit balances when an ACH debit starts (better UX, risk of returns) or when it settles (safer, 1-4 day delay)?

  8) suggestions and plan to move forward (when we're ready to implement)
    i) My recommendations on the open questions:
      a) Use Supabase for database, auth, realtime and storage. One dashboard, one SDK, free tier, Expo support. We can split services out later if needed.
      b) Keep business logic in our own Hono API, not in Supabase database functions, so domain.ts stays the single source of rules and stays unit-testable. Supabase is used as Postgres + auth + realtime, not as the rules engine.
      c) Start with Stripe for both cards and bank debits (test mode). Apply for Stripe Issuing access on day one because approval can take time; if it stalls, switch the card piece to Lithic's sandbox. The card provider sits behind one small module so swapping is cheap.
      d) For the demo, credit balances when an ACH debit starts and handle returns as failed charges. Revisit before any live money.
      e) Don't block Phase 1 on payments. Real accounts + multi-phone sync with simulated money is already a big demo upgrade.
    ii) Repo layout:
      a) server/            new Hono API (routes, db queries, webhooks, jobs)
      b) shared/            domain.ts, split.ts, money.ts moved here and imported by both mobile/ and server/ (or keep them in mobile/src/lib and import by path at first)
      c) server/migrations/ SQL migrations for the tables in section 4 (Supabase CLI or drizzle-kit)
      d) mobile/src/lib/api.ts keeps the same method names; add an HTTP implementation and choose fake vs real with an env var (EXPO_PUBLIC_API_URL set = real backend). The fake backend stays for offline demos and UI work.
    iii) Step-by-step, Phase 1 (no money, about 2-4 days of focused work):
      1. Create the Supabase project; turn on email + phone OTP auth. Add SUPABASE_URL / keys to .env files (never committed).
      2. Write migrations for section 4 tables; seed the demo users and groups for testing.
      3. Scaffold server/ with Hono: auth middleware (verify Supabase JWT -> actor id), Idempotency-Key handling, error format matching ApiError messages the app already shows.
      4. Persistence layer: load a group's state from Postgres into the Db shape domain.ts expects, run the domain function inside a transaction with the group row locked (SELECT ... FOR UPDATE), write the changes back, append ledger + audit rows. This lets us reuse domain.ts almost unchanged at first.
      5. Implement endpoints in section 2 in this order: /me and search, groups + invites, deposits/withdrawals, purchase (simulated card tap endpoint for now), claim board, proposals/accept, budget proposals, chargeback.
      6. Port tests: run tests/domain.test.ts against domain.ts as today, plus API tests that hit the endpoints against a local Supabase (supabase start).
      7. App: sign-in screen, HTTP api.ts, subscribe to Realtime for the selected group and refetch on changes; remove the demo switcher when the real backend is on.
      8. Demo check: two phones (or a phone + web) in the same group, claiming items and locking in live.
    iv) Phase 2 (about 2-3 days): Inngest jobs for period rollover and the 7-day deadline (idempotent per group + period); Expo push tokens table + notifications for invites, new charges, item edits, proposals; invite email/SMS; receipt upload to Storage + vision OCR endpoint with a JSON schema, total check, and a fallback to a single editable line.
    v) Phase 3 (test-mode money, about 3-5 days once Stripe access is granted): Stripe Connect/Issuing setup, cardholder + card creation on invite accept, issuing_authorization.request webhook calling purchaseBlocker()/spendLimit() (keep it fast: one indexed query + the pure function), transaction/capture webhook to update the charge amount, Financial Connections bank linking in the app, saved personal card for debt recovery, ACH debits for deposits/refills with webhook-driven success/failure/return, nightly reconciliation comparing our ledger to Stripe.
    vi) Accounts to set up before starting: Supabase project, Stripe account (request Issuing access), Inngest, Expo (EAS) for push credentials, an LLM provider key for OCR, Resend + Twilio (optional for the demo), Sentry.
    vii) Definition of done for "backend v1" (end of Phase 1-2): two people on two devices can create a group, invite and accept, make a simulated purchase, claim items and lock in live, settle, see balances update everywhere, roll a period, and get push notifications, with all rules enforced on the server and tests passing.
    viii) Who could own what (suggestion): one person on database + server endpoints, one on app integration (auth, HTTP api.ts, realtime), one on jobs/notifications/OCR, then everyone on Stripe in Phase 3.
