Launch plan: getting Split Bill onto a real group's iPhones (research, October 17, 2026; nothing here is built yet)
  Goal: decide which APIs and hosting we can use right away, and list every step between today's fake-backend app and a real group using it on their own phones. Builds on backend.txt (server design) and follows schema.txt as updated by Saahil on October 17 (spend rule by share, cardholder sends the first proposal, personal card charged when a split takes someone below $0).

  0) at a glance
    i) There are two milestones, and only the first can start today.
      a) Milestone A: real app, real accounts, a real group on their own iPhones, test-mode money. No approvals needed. About 1-2 weeks of work.
      b) Milestone B: real cards paying at real stores. Gated on outside approvals and legal work. Weeks to months.
    ii) Why B is blocked:
      a) Apple Pay won't work with test cards. Stripe: digital wallet tokens "are only available in live mode", so nobody can add a test card to Apple Wallet.
      b) Stripe's live Issuing is for commercial (business) card programs. Consumer cards are a private preview, and live access means applying to Stripe sales as a company.
      c) Pooled group money held for consumers likely counts as money transmission / stored value, so a live launch needs a partner bank and legal review (backend.txt 7.iii).
    For the hackathon deadline (10:00am October 18), see section 8: a cut-down version of milestone A that fits in 17 hours.
    iii) How purchases work in A: a "Simulate tap" button in the app calls Stripe's test endpoint (POST /v1/test_helpers/issuing/authorizations). Stripe then sends our server the same real-time issuing_authorization.request a real card swipe would, so our rules (purchaseBlocker / spendLimit) run exactly as they will in production. Only the store is fake.

  1) APIs we can use right away (no approval needed)
    i) Database, sign-in, live updates, receipt photos: Supabase. Free tier pauses a project after about a week with no activity, so move to Pro ($25/mo) once the group is using it.
    ii) Sign-in method: Supabase email one-time code, or Sign in with Apple. Phone codes need an SMS provider (Twilio) that charges per text, so skip them at first.
    iii) API server: Hono (TypeScript) importing domain.ts and split.ts unchanged, as planned in backend.txt.
    iv) Test cards and approving each tap: Stripe Issuing in test mode. Instant access from the Stripe dashboard (US). Create cardholders and virtual cards, simulate taps and captures, answer the real-time authorization webhook. Test cards can't be used at real merchants.
    v) Saved personal card for debt recovery (schema 3.iii): Stripe SetupIntent at sign-up, PaymentIntent when a split takes someone below $0. Works in test mode now and in live mode with a normal Stripe account.
    vi) Bank linking and ACH deposits/refills: Stripe Financial Connections + ACH Direct Debit. Works in test mode. Deposits can also stay simulated in Phase 1.
    vii) Push notifications: Expo Push (expo-notifications). Needs a development build on the phone, not Expo Go.
    viii) Scheduled jobs (period rollover, 7-day deadline, sending stale draft splits): Inngest. [Simpler: Vercel Cron.] Free tier is enough.
    ix) Receipt scanning (schema 6.i.a): a vision model on the server, e.g. Claude Sonnet 5.5, returning structured JSON, checked against the charge total.
    x) Errors: Sentry, free tier.
    xi) Backup card issuers if Stripe stalls: Lithic (self-serve sandbox, Auth Stream Access for real-time approval) and Increase (self-serve sandbox, real-time decisions). Both gate production access too.

  2) hosting
    i) API: Railway or Vercel. Stripe needs an answer to each tap within about 2 seconds, so an always-running server (Railway) or Vercel's reused instances (Fluid Compute) avoids slow cold starts on that endpoint.
    ii) Database, sign-in, storage, live updates: Supabase.
    iii) iOS builds: EAS Build, then EAS Submit to TestFlight.

  3) steps to milestone A (a real group on real iPhones, test-mode money)
    i) Accounts (day 1):
      a) Apple Developer Program, $99/yr, ideally enrolled as a company. Apple's rules expect financial apps on the App Store to come from a legal entity.
      b) Expo / EAS account.
      c) Supabase project.
      d) Stripe account with Issuing test mode turned on. Also contact Stripe sales about live Issuing now, because approval takes time and test access doesn't register interest in live mode.
      e) Inngest, Sentry, and an LLM API key.
    ii) Backend, Phase 1 (about 2-4 days, backend.txt 8.iii):
      a) Postgres tables from backend.txt section 4, including funded_period, sent_at, notifications and payment_methods.
      b) Sign-in check on every request (verify Supabase JWT -> actor id), Idempotency-Key handling.
      c) Endpoints from backend.txt section 2 running domain.ts.
      d) Realtime updates for the claim board, locks, edits and proposals.
    iii) App (in parallel):
      a) Sign-in screen.
      b) HTTP version of api.ts, switched on by EXPO_PUBLIC_API_URL so the fake backend stays for offline demos.
      c) Subscribe to Realtime for the selected group and refetch on changes.
      d) Hide the demo user switcher when the real backend is on.
    iv) Stripe test mode:
      a) Create a cardholder and virtual card when someone accepts an invite.
      b) issuing_authorization.request endpoint calling purchaseBlocker() / spendLimit(); creates the cardholder's draft charge.
      c) "Simulate tap" button that calls the test authorization endpoint.
      d) Save each member's personal card (SetupIntent) for debt recovery.
    v) Phase 2 work:
      a) Expo push for invites, sent proposals, receipt scans, item edits and budget changes.
      b) Inngest jobs: period rollover, 7-day deadline, send-stale-drafts (10 minutes).
      c) Receipt upload to Supabase Storage + vision OCR.
    vi) Build and ship:
      a) app.json: add the expo-notifications plugin; confirm the bundle ID com.henryehrnman.splitbill is ours.
      b) eas build --platform ios, then eas submit to TestFlight.
      c) Add the group as internal testers: up to 100 people, no Apple review, but each must be added to our App Store Connect team. External testers (up to 10,000) need a one-time beta review. Builds expire after 90 days.
    vii) Test with the group: create a group, invite and accept, simulate a tap, send the first proposal, claim and lock items live on two phones, settle, roll a period, get push notifications.

  4) steps to milestone B (real money)
    i) Form a company (needed for Stripe live Issuing and for App Store review of a financial app).
    ii) Apply to Stripe sales for live Issuing (or to Lithic / Increase).
    iii) Legal review of pooled funds. Likely answer: a partner bank or banking-as-a-service provider holds the money.
    iv) Basic Apple Pay: users type the card into Apple Wallet themselves (manual provisioning). Needs Apple approval through Stripe, about 1-2 weeks.
    v) "Add to Apple Wallet" button (push provisioning): needs the Apple entitlement com.apple.developer.payment-pass-provisioning, requested by emailing support-issuing@stripe.com with card network, card name, app name, Apple team ID, App Store app ID (ADAM ID) and bundle ID. Then use AddToWalletButton from @stripe/stripe-react-native. On iOS the button flow can be built early with testEnv={true}, but no card is actually added.
    vi) Identity checks for cardholders (Stripe Identity), live keys, ledger reconciliation against Stripe.
    vii) Possible early real-money pilot: our own team using company cards for team expenses is a genuine business use. Ask Stripe sales whether that qualifies.

  5) costs to expect for milestone A
    i) Apple Developer Program: $99/yr.
    ii) Supabase: free to start, $25/mo Pro once in use (avoids the inactivity pause).
    iii) Railway or Vercel: free to a few dollars a month at this size.
    iv) Stripe test mode, Expo Push, Inngest and Sentry free tiers: $0.
    v) LLM receipt scanning: pay per use, small at this size.
    vi) EAS Build: free tier covers a handful of builds a month.

  6) decisions for the team
    i) Accept that the first TestFlight round uses simulated taps (recommended), or wait for live approval.
    ii) Railway or Vercel for the API.
    iii) Keep deposits simulated in Phase 1, or build Financial Connections right away.
    iv) Who forms the company and contacts Stripe sales this week, since that's the slowest step.

  8) hackathon plan: 5:00pm October 17 to 10:00am October 18 (17 hours)
    Goal for 10am: a group opens Split Bill on their own iPhones, signs in as themselves, and uses one shared group live: invite and accept, simulate a card tap, the payer sends the first proposal, everyone claims receipt items from a real photo and locks in, the split settles and balances update on every phone. All rules run on a real server, money stays simulated. Everything in sections 3-4 that isn't on this list waits until after the hackathon.

    i) research findings that shape the plan
      a) Expo Go is out for the group. Our app is on Expo SDK 58 (stable October 15). Expo's SDK 58 post says the App Store Expo Go for SDK 58 ships "within a few weeks"; today's store version runs SDK 57. Since SDK 57, iOS Expo Go also requires the phone and the computer running the dev server to be signed in to the same Expo account, so teammates can't just scan a QR code.
      b) TestFlight only works if someone already has a paid Apple Developer membership. Apple says enrollment takes about 2 business days; 2026 forum reports describe 1-7+ weeks. If nobody has one, don't plan on TestFlight.
      c) The hosted web app works on any iPhone today. The app already exports for web (dist/). Served from a URL, it opens in Safari and can be added to the home screen, which needs no Apple account, no review and no installs. This is the main path.
      d) Supabase's built-in email sender allows about 2 auth emails per hour for the whole project, and only to team addresses. So no email codes or magic links: use email + password with "Confirm email" turned off (no emails sent), or anonymous sign-in.
      e) Native push needs a development build (and an Apple account on iOS). Skip it: the app's in-app notifications (domain.ts notificationsFor) plus Realtime give live updates while the app is open.
      f) domain.ts, split.ts, money.ts, fakeOcr.ts and seed.ts already use explicit .ts imports and plain TypeScript, so they run unchanged in Deno (Supabase Edge Functions) and in Node 24.
      g) Stripe Issuing test mode is instant from the dashboard, and simulated taps fire the real issuing_authorization.request webhook (section 0.iii). It's a stretch goal: worth it only once the core works.

    ii) architecture for tonight (fastest path that keeps domain.ts as the single source of rules)
      a) Database: one Supabase Postgres table, app_state(id int primary key, db jsonb, version int), holding the same Db object the fake backend keeps in AsyncStorage today. The normalized tables in backend.txt section 4 come after the hackathon.
      b) Server: one Supabase Edge Function, rpc. Request: {method, args} plus the user's Supabase JWT. It looks up the caller's domain user id from the JWT (never trusts an actor in the body), loads app_state, runs tick() and the same domain function api.ts calls today, and saves with an optimistic version check (retry on conflict). Then it returns the Db filtered to the caller's groups and users.
      c) Shared code: a small script copies mobile/src/lib/{domain,split,money,fakeOcr,seed}.ts into supabase/functions/_shared/ before each deploy (Supabase's recommended layout), so there's still one copy we edit.
      d) Sign-in: Supabase email + password, confirmations off. Sign-up creates the domain User (name, handle, email, phone) through a createUser rpc method. Keep the demo user switcher behind a "demo mode" toggle for judges.
      e) Live updates: each app subscribes to Supabase Realtime postgres_changes on app_state and calls rpc fetch when it changes.
      f) App: api.ts gets an HTTP implementation with the same method names, chosen by EXPO_PUBLIC_API_URL; the fake backend stays for offline demos.
      g) Receipt scanning: a second Edge Function, scan-receipt. The app picks or takes a photo with expo-image-picker (works on web and iOS) and uploads it. The function asks a vision model (Claude Sonnet 5.5, or Haiku 5.5 for speed) for JSON items/tax/tip, checks the sum against the charge, and falls back to the editable single line when it doesn't add up. The model key lives only in the function's secrets.
      h) Web hosting: npx expo export -p web, deployed to Vercel (static, free Hobby plan) or EAS Hosting (eas deploy). Redeploy after every merge so the URL on everyone's phone stays current.

    iii) accounts and keys (first 45 minutes, in parallel)
      a) Supabase project (free tier is fine for one night): turn off email confirmations, enable Realtime on app_state, note the URL, publishable key and secret key.
      b) Vercel (or Expo) account for the web URL.
      c) Anthropic API key for receipt scanning.
      d) Check whether anyone already has an active Apple Developer membership. Yes: run the native track in v.d. No: web only, and don't enroll tonight expecting it to arrive.
      e) Optional: Stripe account with Issuing test mode, only if the stretch goal happens.
      f) .env files stay out of git (.gitignore already covers .env*).

    vi) cut list (don't start these before 10am)
      Real money and live cards; Apple Pay / Add to Wallet; native push; Stripe Financial Connections / ACH; saved personal card for debt recovery (keep simulated); Inngest jobs (tick() already runs period rollover, the 7-day deadline and stale drafts on every request); normalized tables, ledger reconciliation, row-level security per group; natural-language claiming and other AI ideas beyond receipt scanning.

    vii) risks and fallbacks
      a) Two writes at once on the single app_state row: the version check plus a retry handles it at hackathon scale.
      b) Edge Function cold start or outage during the demo: keep the fake backend build ready (EXPO_PUBLIC_API_URL unset) and the backup video.
      c) Receipt scan returns something wrong: totals are checked against the charge, and items can be fixed by hand before claiming (already built).
      d) Privacy: the rpc function must filter responses to the caller's groups; it's the one security step we can't skip, since real people will sign in.
      e) Judges without accounts: demo mode with the seeded users stays available on the same URL.

Real cards need live Stripe Issuing approval (business programs only), Apple's wallet approval, and a partner bank for pooled funds (sections 0.ii and 4). The rules engine that would approve real taps is the same code running tonight.
